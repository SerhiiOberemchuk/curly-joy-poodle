# Архітектура

Обов’язкові вимоги до змін: [coding-standards.md](./coding-standards.md).

## Стек і межі

Next.js 16.4.1 App Router, React 19.3, TypeScript 7, ESLint 9, CSS Modules.
Маршрути в `src/app` компонують сторінки; бізнес-логіка зберігається у
`src/features/catalog`, `cart`, `checkout`, `business`, `customer-account`,
`home` та `favorites`.
Спільний layout містить шапку, `main#main-content` і підвал.

CRM є джерелом каталогу, цін, залишків, замовлень, платежів і доставки.
`src/lib/crm-client.ts` виконує серверні запити й повертає `unknown`;
адаптери перевіряють відповіді схемами Zod. Секрети захищені `server-only`.
Взаємодія браузера з бізнес-логікою використовує Server Functions / Actions.

## Бібліотеки

- React Hook Form, Zod, resolvers — форми та спільна валідація.
- react-select — доступні поля пошуку міста, відділення й вулиці.
- SWR, use-debounce — довідники, пошук і перевірка оплати.
- Iron Session — зашифровані сесії та токени оформлення/повернення.
- sanitize-html — очищення HTML описів; текстові теги без атрибутів.
- nuqs — стан фільтрів каталогу в URL.
- Zustand — миттєвий стан кошика й улюблених у браузері.
- @microsoft/clarity — теплові карти й записи сесій (розділ «Аналітика»).

`react-select` використовує Emotion навіть з `unstyled`. Кореневий
`EmotionRegistry` створює окремий cache на рендер, збирає правила через
підтримуваний `cache.insert` та передає їх у `useServerInsertedHTML` перед
відповідною порцією HTML. `cache.compat` запобігає inline-тегам `style`
всередині полів, які спричиняють розбіжність гідратації у streaming checkout.
Клієнт підхоплює серверні правила за `data-emotion`; CSS Modules залишаються
основою оформлення. Адаптер потрібен для зв'язку Emotion з App Router;
власного механізму CSS-in-JS або вимкнення SSR полів немає.

## Улюблені

`favorites-store.ts` створює окремий Zustand store для кожного `FavoritesProvider`;
серверні запити не ділять глобальний стан. Компоненти використовують селектори:
сердечко читає належність одного товару, шапка — кількість, сторінка — список ID.
У сховищі немає копій цін, залишків або об'єктів каталогу.

Zustand `persist` зберігає лише `ids` у `localStorage` під ключем
`curly-joy-favorites`. Завантаження починається після монтування, щоб серверний
HTML збігався з першим клієнтським рендером. До завантаження кнопки недоступні,
а сторінка показує стан завантаження замість помилкового порожнього списку.

`favorites-storage.ts` — адаптер стандартного `PersistStorage`: він потрібен
для читання старого формату `string[]` під тим самим ключем. Перший запис
переходить на `{state: {ids: string[]}, version: 1}`. ID очищуються від
дублікатів і некоректних елементів зі збереженням порядку. Читання не записує
дані назад; події `storage`, зокрема очищення сховища, перечитують актуальний
список без циклу записів. Паралельні зміни в різних вкладках мають семантику
останнього запису; це локальний список, без серверного вирішення конфліктів.

Якщо сховище недоступне або переповнене, зміни залишаються в пам'яті вкладки,
а спільне повідомлення пояснює, що вони не збережені. Наступний успішний запис
зберігає весь поточний список і прибирає помилку. Пошкоджені або невідомі версії
даних не перезаписуються під час завантаження. Статуси завантаження й помилок
не зберігаються; їх оновлення не викликає запису в браузер.

Синхронізації улюблених із CRM зараз немає. Коли CRM надасть контракт та
ідентифікацію покупця, до фічі потрібно додати Server Actions і правила
об'єднання гостьового списку, повторів, конфліктів та очищення при виході.
UI залежить від стану й операції `toggle`, а браузерний формат ізольований
в адаптері; контракт CRM не потрібно закладати в компоненти товарів.

## Пошук, фільтри й картка товару

Кнопка «Каталог» у хедері (на телефоні — смуга «Каталог товарів») відкриває
випадаючий каталог (`src/features/catalog/components/catalog-menu.tsx`):
«Усі товари», «Новинки», «Зі знижкою» (лише коли в CRM є стара ціна вище
поточної), живі добірки CRM і категорії верхнього рівня з фото та їхніми
підкатегоріями. Підкатегорії й добірки з’являються самі, щойно вони є в CRM.
Дані — кешований каталог (`getCatalogMenu`), тож панель і її посилання є в
статичному HTML кожної сторінки. Хедер є й на сторінках помилок, тому збій
читання CRM лишає в панелі лише «Усі товари» й «Новинки», а не ламає сторінку.
Панель — нативний `popover`: відкривається, закривається Escape чи кліком
поза нею й повертає фокус кнопці без JavaScript; клієнтський перехід за
посиланням у ній закриває її. Вона прив’язана до нижнього краю смуги хедера
CSS anchor positioning і йде за нею, коли та стискається; без підтримки
anchor positioning стоїть під повним хедером.

Пошук у хедері поза каталогом показує підказки: Server Function
`searchSuggestionsAction` (`src/features/catalog/search.actions.ts`) читає
кешований каталог тим самим `getProducts({ query })`, що й сторінка
результатів, і повертає перші 5 товарів та загальну кількість. Клієнт
викликає її через SWR після паузи `use-debounce`. Це звичайне поле пошуку
з панеллю посилань, а не combobox: стрілки переводять фокус між
посиланнями, Escape закриває панель. У самому каталозі поле, як і раніше,
оновлює список під час набору.

Фільтри каталогу (категорія, бренд, ціна, наявність, знижка) і сторінки
зберігаються в URL через `nuqs` і застосовуються в браузері до вже
завантаженого списку (`src/features/catalog/filtering.ts`), так само як
сортування. Розділ фільтра з’являється, лише коли товари в ньому
відрізняються.

Одна картка `ProductCard` на всіх списках. Кнопка кошика на картці
додає товар з одним варіантом наявним `addToCartAction` (сервер повторно
перевіряє залишок); товар з розмірами чи кольорами вона відкриває на
сторінці товару.

Поле телефону checkout форматує введення `formatPhoneInput`
(`src/features/checkout/validation.ts`): «+38 0XX XXX XX XX», зайві цифри
відкидаються. Це виняток зі стандарту бібліотек: потрібен один фіксований
формат, а перевірку й нормалізацію вже робить `normalizePhone` на клієнті
й сервері; окрема бібліотека масок дала б залежність для одного поля.

## Дані й кеш

Загальні списки каталогу використовують `"use cache"`, `cacheLife("minutes")`
і теги `catalog`, `catalog:collection:<slug>`. Ціни й залишки на сторінці товару
читаються зі спільного для всіх відвідувачів `'use cache: remote'` на 30–60 с
з тегом `catalog`: CRM дає одну квоту запитів на токен для всього сайту, тож
перегляди товарів (будь-який трафік і вигадані slug) коштують їй не більше
двох читань каталогу на хвилину. Помилка CRM не кешується. Персональні дані,
додавання товару, відкриття кошика та checkout читають CRM наживо, поза кешем.
Зміна кількості й видалення у відкритому кошику перераховуються в Zustand
без звернення до CRM та без Server Action.
Склад набору (`GET /products/{id}` для bundle) — описові дані, як і список:
`'use cache: remote'`, `cacheLife("minutes")`, тег `catalog`, тож він входить
у пререндер сторінки товару.
Обробника вебхука `catalog.changed` у проєкті поки немає; тег дає змогу
скидати кеш, коли він з’явиться.
CRM транспорт використовує `cache: "no-store"`.
Неповна або некоректна пагінація завершує читання помилкою.

Cookie `cjp_cart_v2` містить `{revision, lines: [{p: variantId, q: quantity}]}`:
позиції та UUID ревізії змінюються одним записом. Старий масив позицій також
читається й отримує ревізію при редагуванні або перед надсиланням checkout.
Браузер записує його після локальної зміни, щоб прямий перехід на checkout
бачив той самий кошик. Запис змінює лише відредаговану позицію: позиції,
змінені в іншій вкладці або не показані на сторінці, зберігаються без
попереджень. Якщо cookie не прийняв зміну, кошик повертає попередню кількість.
Покупця не просять перезавантажувати сторінку: склад, ціни й залишки
перевіряє checkout під час відкриття та підтвердження замовлення, а Server
Action сам оновлює форму через `refresh()`. Посилання на checkout виконує звичайну навігацію,
щоб не взяти старі дані з клієнтського кешу Next.js. Старий HttpOnly cookie `cjp_cart` читається лише до
першого запису нового формату. Порожній новий cookie містить `lines: []`, щоб старий
кошик не з’явився знову. Сервер перевіряє формат cookie й актуальні ціни та
залишки через CRM при відкритті кошика і перед замовленням.
Нульовий залишок не приховує товар,
але забороняє покупку. `stock: null` означає, що облік кількості не ведеться.
Сума обчислюється в цілих копійках із перевіркою безпечного діапазону.

## Стрімінг і скелетони

`loading.tsx` не використовується: сторінка ніколи не підміняється одним
загальним станом завантаження. Усе, що читає кешовані дані CRM (`minutes` і
довше) або власний вміст магазину, рендериться без `<Suspense>` і потрапляє
в пререндер: заголовки, хлібні крихти, опис і галерея товару, характеристики,
склад набору, рекомендації, плитки категорій, соціальні докази, інфосторінки.
Окремими межами `<Suspense>` стрімляться лише дані, яких немає в статичному
shell:

| Що | Чому під час запиту | Що показує shell |
| --- | --- | --- |
| Ціна, наявність, кнопка кошика й JSON-LD товару | кеш 30 с | `AddToCartFormSkeleton` з назвами варіантів із кешу |
| Поріг безкоштовної доставки (шапка, головна, товар, `/info/delivery`) | кеш 30 с | загальне формулювання тієї ж форми |
| Рейтинг товару | кеш 60 с | окремий скелетон зведення; форма не чекає рейтинг |
| Список відгуків | кеш 60 с, `?reviewsPage` | картки за кешованою кількістю; сторінка списку не затримує зведення |
| Форма відгуку | id запиту | ті самі поля, заблоковані лише до отримання id, без очікування CRM-відгуків |
| Фільтри каталогу | набір товарів залежить від URL | окремий скелетон полів зі справжніми підписами; навігація категорій і мобільний перемикач вже працюють |
| Результати каталогу | `?q=`, добірка й стан URL | окремий `CatalogResultsSkeleton`; фільтри та результати ділять одне читання через `React.cache` |
| Кошик | cookie, актуальні ціни й залишки | скелетон позицій; рекомендації мають власну межу і не затримують перевірений кошик |
| Checkout | cookie, перевірений кошик та capabilities CRM | справжні назви кроків, підписи й заблоковані поля контактів; скелетони способів, товарів та сум |
| Статус замовлення | приватний receipt і поточний стан CRM | одна постійна картка з нейтральним `h1`; скелетони стану, номера, деталей і дій |

Межа відповідає незалежній області інтерфейсу, а не кожному `await` чи полю.
Ціна, наявність і дія покупки є узгодженим блоком; checkout також перевіряє
товари й умови з одного `loadCart`, а не створює різні фінансові знімки для
окремих колонок. Постійні підписи checkout використовують спільні
`CheckoutStepLegend` і `Field`; поки CRM перевіряє можливість оформлення,
поля заблоковані й не можуть втратити введення при заміні fallback.

`cacheLife("minutes")` має `stale: 300`, `revalidate: 60`, `expire: 3600`:
хвилинна ревалідація сама по собі не виключає дані з shell. За встановленим
Next.js `expire < 300` або `revalidate: 0` виключає дані з пререндеру;
`30 <= stale < 300` допускає пререндер, але виключає спільний App Shell.
`params`-маршрути з `instant = false` залишаються явним винятком для
404/redirect, описаним у розділі SEO; це не гарантія миттєвої навігації.

Скелетон будується з тих самих класів і елементів, що й готовий блок, і лежить
у файлі цього блоку. Де форму блоку визначають дані, скелетон бере їх із кешу:
каталог рахує картки першої сторінки в порядку `defaultSort` і для кожної —
бренд, варіанти, наявність і стару ціну (`cardShape`), поля фільтрів — за
тими самими правилами `filterSections`, що й панель. Після читання URL
скелетон пошуку обмежується одним адаптивним рядом: кількість результатів
ще невідома, тому він не резервує шість рядів звичайного каталогу.
Геометрія відгуків бере лише кількості з `getReviewCountsForShell`
(`cacheLife("minutes")`) через спільне пакетне читання рейтингів каталогу,
без окремого CRM-запиту для скелетона кожного товару. Тексти, автори й
рейтинг зберігають короткий кеш.
Рядки, які стрімляться з
довшим текстом, тримають місце `min-height: 2lh`. Заголовок і плитки
каталогу є в HTML один раз. Пошук `?q=` додає власний заголовок
(`SearchHeading`, читає URL через `useSearchParams()`), а його позначка
`data-catalog-search` CSS-правилом ховає заголовок сторінки й плитки; при
переході з шапки пошуковий заголовок є одразу, без серверного стріму.
Клієнтські списки з `localStorage`/`sessionStorage` (обране, «Ви переглядали»)
до читання сховища показують один ряд або полицю скелетонів. Рейтинг картки
має кісточку під час `SWR.isLoading`, після відповіді без відгуків або помилки
залишається зарезервований рядок без вигаданої оцінки. Це локальні стани
клієнтських бібліотек: звичайний SWR не активує зовнішній Suspense.

Попередня перевірка до уточнення меж виконувалася у браузері (`next dev`, cookie
`next-instant-navigation-testing` заморожує статичний shell): позиції
заголовків, секцій і підвалу у shell і після завантаження збігаються на
ширинах 390, 768, 1024 і 1400 px для головної, каталогу, категорій, товару,
набору, `/info/delivery`, обраного й checkout. Невідворотні відхилення:
довгі назви в кошику та прогрес до безкоштовної доставки (їх немає в cookie),
кількість відгуків, пошук при прямому відкритті `/catalog?q=` і поява
«Ви переглядали» над підвалом після читання історії вкладки.

Повторна перевірка 2026-11-12: у `next dev` на 1440 px звичайний каталог
має один видимий `h1`, без горизонтального overflow, підвал у shell і після
відповіді розташований на однаковій висоті (3453 px). Для порожнього пошуку
після гідратації shell має один ряд і підвал на 973 px, готовий стан —
на 746 px: невідому кількість результатів не оголошуємо нульовою наперед.
На 390 px перевірено початковий shell без overflow та відкриття статичних
категорій клавіатурою до завантаження полів. Після цього браузерний конектор
втратив з’єднання; готовий мобільний стан, checkout, картку статусу й нові
межі відгуків після цієї зміни в браузері ще не перевірено. Серверні тести
з відкладеними Promise окремо перевіряють незалежну віддачу кошика, картки
статусу й форми відгуку; це не замінює browser QA або перевірку банку.

Плавну зміну сторінки (`PageTransition`, React `ViewTransition`) кожна
`page.tsx` і `not-found.tsx` ставить навколо себе, а не root layout. Обгортка в
layout мала ключ `usePathname()`; у статичному shell шлях невідомий, тому вона
рендерилася в fallback зі сторінкою всередині й ще раз у стрімі, і HTML
кожної сторінки містив дві копії вмісту (два `h1`, двічі JSON-LD; на головній
~120 КБ зайвого). Сторінка монтується заново на кожен новий шлях, тож її
переходу ключ не потрібен.

Посилання картки позначає навігацію типом `open-product`. У цьому переході
CSS надає фото активованої картки й головному фото галереї спільне ім’я
`product-photo`. Браузер за 360 мс змінює розмір і положення між знімками.
Фокус посилання визначає джерело, навіть коли товар є в кількох списках.
Картка передає галереї `currentSrc` завантаженої мініатюри. Якщо оригінал
фото збігається, галерея показує цю мініатюру до `onLoad` великого
зображення в `next/image`, який спрацьовує після декодування. Браузер
анімує рамку з фото, тому мініатюра залишається видимою і під час руху,
і після нього, поки завантажується чіткіша версія.
За `prefers-reduced-motion: reduce` фото відкривається одразу.

Під час гортання галерея тримає попереднє фото під новим до його
декодування, а потім проявляє нове за 240 мс. Повноекранний перегляд
відкривається в нативному `dialog` і використовує той самий вибраний
кадр. У ньому працюють стрілки клавіатури, свайп та закриття через Escape.

Після успішної Server Action форма покупки й швидке додавання з картки
запускають декоративний політ до видимої іконки кошика. Політ використовує
завантажене фото, а пудель та дві іскри з’являються один раз за сесію вкладки.
Якщо фото недоступне, іконка реагує на місці. За зменшеного руху анімація
пропускається. Лічильник показує підтверджену кількість одразу після відповіді.

## Спливаючі поверхні та рух

`src/components/ui/surface-motion.module.css` задає спільну появу й закриття
меню каталогу, контактного popover, мобільного меню, панелі пошуку, підказок
та модалки пропозиції. Токени в `globals.css`: відкриття 320 мс із м’яким
уповільненням, закриття 200 мс, поява списків react-select 220 мс. Зміщення
6–14 px і масштаб від 0.985 до 1; широке меню каталогу не масштабується,
щоб зберігати чіткість тексту. Рух і затухання вимикаються за
`prefers-reduced-motion`; стабільний gutter запобігає зсуву сторінки при
блокуванні прокручування модалкою.

Popover зберігає нативне закриття зовнішнім натисканням; popover і dialog —
Escape та керування фокусом.
`@starting-style` та дискретні переходи `display`/`overlay` дають браузеру
домалювати вихід після логічного закриття. Браузери без цієї підтримки
отримують звичайне миттєве закриття. Опис механізму:
[MDN dialog animations](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog#animating_dialogs).
Малий спільний адаптер `surface-interaction.ts` вмикає `inert` після події
`toggle` закриття й знімає перед відкриттям у `beforetoggle`: CSS утримує
поверхню видимою на час виходу, тож самих `pointer-events` недостатньо для
блокування Tab. Нативне повернення фокуса завершується перед `inert`;
адаптер не реалізує власний focus trap або життєвий цикл.
Мобільне меню й підказки залишаються в DOM із `hidden`, `inert` та
`aria-hidden`, тому під час виходу не приймають фокус або натискання.
Закриті підказки не запускають пошукових запитів і не перехоплюють стрілки.
Адаптивний пошук дзеркалить у `inert` лише межу фокуса CSS-breakpoint через
`matchMedia`; на десктопі поле доступне незалежно від мобільного перемикача.
Таймерів присутності й дубльованого viewport-стану немає.

React-select підключає анімацію появи через підтримуваний `classNames.menu`,
з напрямком відповідно до `placement`. Закриття й видалення listbox лишаються
бібліотеці; фокус, вибір і клавіатурна взаємодія не затримуються.

Локальна перевірка 2026-11-12: Chrome, desktop 1440 px і mobile 390 px —
відкриття/закриття каталогу, контактів, мобільного меню й пошуку, клавіатура
та Escape у підказках і сортуванні. Поведінку закритих панелей, SWR і
responsive-межі перевіряють компонентні тести. CRM зараз не повертає активної
welcome-пропозиції, тому її нативну поведінку перевірено компонентними
тестами, а візуальну анімацію модалки в браузері ще не перевірено. Safari,
реальний touch-пристрій і системний reduced-motion окремо не перевірялися.

## Checkout і оплата

Checkout перевіряє актуальний кошик, суму, доступні способи та refs адреси.
Якщо сума, кількість або показані умови безкоштовної доставки змінилися,
покупець підтверджує оновлену форму. Зміна доступних способів у CRM оновлює
вибір форми, очищає залежні поля адреси та застарілу знижку для іншої доставки.
Захищений токен форми забезпечує однаковий externalId для паралельних повторів
того самого запиту; завершена покупка не блокує нове замовлення з нової форми.
CRM присвоює номер замовлення й створює посилання Monobank.

Повернення використовує `/checkout/success?token=…`; токен дає доступ лише до
одного замовлення протягом 24 годин. Статус і сума читаються з CRM.
Посилання після відмови банку й COD також містять токен; стара сторінка без
токена перенаправляє на захищену адресу для замовлення з наявної сесії.
Токен зберігає також спосіб оплати та, для нового кошика, його ревізію.
Без cookie замовлення відновлюється через токен; сесія записується лише в Server Action.
Відсутній/нечинний токен і відсутня сесія показують відновлення, а не 404.
Затримка банку показує індикатор і перевірку кожні 5 секунд до хвилини.
Server Action повертає ревізію кошика лише після підтвердження оплати або COD.
Браузер очищає кошик синхронно, тільки якщо поточна ревізія збігається з
купленою. Серверна синхронізація платежу не записує cart cookie, тому її
затримана відповідь не перезаписує новий кошик. Старі квитанції без ревізії
не дозволяють автоматичного очищення. Незмінена квитанція не перезаписується.

Локального журналу замовлень, банківського callback і mock-провайдерів немає.
Webhook банку та створення ТТН належать CRM. Подробиці: [crm-checkout.md](./crm-checkout.md).

## Запит на оптовий доступ (B2B)

`/business` — форма запиту для зоомагазинів, грумерів, ветклінік. Заявка
стає лідом CRM із джерелом `partner` (`POST /leads`, `source: "partner"`),
окремо від роздрібних звернень. Ключ ідемпотентності `b2b-<uuid>` генерує
браузер один раз на форму, тож повторне натискання не створює дубль.
Менеджер узгоджує умови, оформлює контрагента й запрошує партнера до
кабінету партнера в CRM. Посилання «Увійти до кабінету партнера» й «Ввести
код» ведуть на `PARTNER_PORTAL_URL` (за замовчуванням
`https://obriym-crm.com/portal`).

Кабінет роздрібного покупця на сайті не будується: це функція Obriym CRM на
адресі магазину (`{shop}.obriym.app`). Варіант кабінету в дизайні сайту
лежить у гілці `feature/customer-cabinet` як платна кастомна доробка.

Адресу кабінету сайт не зберігає: її віддає CRM у `GET /capabilities` →
`customerAccount.url`, лише поки кабінет відкритий (`null`, якщо його вимкнено
чи не налаштовано). Іконка «Особистий кабінет» у шапці й пункт мобільного меню
з’являються тільки тоді. Відповідь кешується на 5 хвилин, тож вмикання й
вимикання в CRM доходить до сайту за 5 хвилин без релізу; коротший кеш змусив
би й статичні сторінки оновлюватися щохвилини, бо шапка є на кожній.
Якщо CRM недоступна, шапка рендериться без іконки
(`src/features/customer-account/queries.ts`).

Checkout починається з контактів і не вимагає входу або підтвердження
профілю. Окремий блок авторизації прибрано після уточнення маркетингового
сценарію. Кабінет лишається зовнішнім сервісом CRM. Попап із контактом,
персональний промокод, серверна перевірка першої покупки та облік
конверсій описані в [promotions-plan.md](./promotions-plan.md).
Реалізований контракт попапа, промокодів, підсумку checkout та налаштування
CRM описані в [promotion-integration.md](./promotion-integration.md).
Відгуки, рейтинг, лічильник клієнтів і скріни з Instagram на головній
описані в [social-proof.md](./social-proof.md).

## Пошукові системи

`src/app/sitemap.ts` збирає головну, каталог, категорії й товари з кешованого
каталогу CRM та інфосторінки; чернетки (`draft` у `src/content/info-pages.ts`)
отримують `noindex` і в sitemap не потрапляють. `src/app/robots.ts` закриває
кошик, checkout, обране й `/api/`. Індексовані сторінки мають canonical:
сортування, колекції й пошук у `/catalog?...` вказують на `/catalog`.

Open Graph будується через `openGraph()` з `src/lib/metadata.ts`: Next
зливає метадані поверхово, тож сторінка, що задає власний `openGraph`, інакше
втратила б назву сайту, локаль і картинку. Загальна картка —
`public/og-image.jpg` (1200×630, вирізана з hero), товар показує своє фото.
JSON-LD товару рендериться поруч із видимою ціною з того самого свіжого
читання; без фото блок `Product` не виводиться (Google вимагає зображення),
хлібні крихти лишаються. `category` у `Product` не передається: Google читає
його як свою таксономію товарів, а назви категорій магазину нею не є
(категорію називають хлібні крихти). Кожна пропозиція й `OnlineStore` мають
`MerchantReturnPolicy` зі сторінки «Повернення»: строк `site.returnDays`
(14 днів, той самий у тексті сторінки й на картці товару), поштою, Україна.
Хто платить за зворотну доставку і `shippingDetails` не вказуються: сайт не
має для них фактів (доставка — за тарифами перевізника); їх задають у Google
Merchant Center. Логотип не передзавантажується й має `sizes`;
головне фото товару — `fetchPriority="high"`.

Колекції CRM мають власні сторінки `/collection/{slug}` (заголовок, опис,
canonical); плитки й полиця рекомендацій на головній ведуть туди, лише коли
колекція жива в CRM, інакше — у каталог. `?collection=` з невідомою назвою
не читає CRM: назва звіряється з кешованим списком колекцій. Товар,
категорія й колекція без тексту в CRM отримують запасний мета-опис. Головна
описує магазин (`OnlineStore`, `WebSite`) даними з `src/lib/site.ts`, товар
має `aggregateRating` з опублікованих відгуків CRM. Іконки — `apple-icon.png`
і `manifest.ts` (192/512 з логотипа). Emotion для react-select підключено
лише в `src/app/checkout/layout.tsx`.

Сторінки товару, категорії, колекції та інфосторінки читають `params` до
першого `<Suspense>` і мають `export const instant = false`. Перевірено на
`next build` + `next start`: з Partial Prefetching перший запит до адреси,
якої не було під час збірки, отримує App Shell зі статусом 200, а `notFound()`
чи `permanentRedirect()` спрацьовують уже в потоці (`noindex` або клієнтське
перенаправлення). Next тим часом рендерить адресу у фоні й кешує результат,
тож кожен наступний запит отримує справжній 404 або 308. Якби `params`
читалися всередині `<Suspense>`, і повторні запити лишалися б 200. Щоб 404
був і з першого запиту, довелося б відмовитися від App Shell для цих маршрутів.

## Аналітика

Microsoft Clarity (`@microsoft/clarity`, проєкт `z4ho5gc47t`) підключає
`src/components/analytics/clarity-analytics.tsx` у кореневому layout, лише
коли `VERCEL_ENV === "production"`: preview-деплої й локальний запуск не
записуються. Clarity сам відстежує клієнтські переходи.

Clarity записує повну адресу кожної сторінки, а адреси checkout містять
токен доступу до замовлення (`/checkout/success?token=…`). Тому документ,
відкритий на `/checkout`, Clarity не завантажує взагалі, навіть після переходу
з нього на інші сторінки. Записаний документ на checkout не потрапляє, бо
checkout відкривається лише звичайною навігацією: посилання з кошика й
повернення з банку. Перетворення цього посилання на `next/link` відкрило б
токен для Clarity.

Введений у поля текст Clarity маскує в режимах Balanced (за замовчуванням)
і Strict; режим Relaxed у налаштуваннях проєкту не вмикати. Сповіщення про
аналітичні cookie — сторінка «Політика cookie».

## Семантика й перевірки

Нативні форми, кнопки, списки, таблиці й заголовки; контакти — `address`,
характеристики замовлення — `dl/dt/dd`. Поля підтримують клавіатуру,
прив’язані назви, повідомлення та фокус помилок.

Перевірки: `npm run typecheck`, `npm run lint -- --max-warnings 0`, `npm test`.
Browser QA, callback банку, production і база даних потребують окремих доказів.
Production build виконується лише за прямим запитом користувача.
