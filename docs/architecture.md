# Архітектура

Обов’язкові вимоги до змін: [coding-standards.md](./coding-standards.md).

## Стек і межі

Next.js 16.4.1 App Router, React 19.3, TypeScript 7, ESLint 9, CSS Modules.
Маршрути в `src/app` компонують сторінки; бізнес-логіка зберігається у
`src/features/catalog`, `cart`, `checkout`, `business`, `customer-account`,
`home` та `favorites`.
Спільний layout містить шапку, `main#main-content` і підвал.

CRM є джерелом каталогу, цін, залишків, замовлень, платежів і доставки.
`src/lib/crm-client.ts` виконує серверні запити й повертає `unknown`;
адаптери перевіряють відповіді схемами Zod. Секрети захищені `server-only`.
Взаємодія браузера з бізнес-логікою використовує Server Functions / Actions.

## Бібліотеки

- React Hook Form, Zod, resolvers — форми та спільна валідація.
- react-select — доступні поля пошуку міста, відділення й вулиці.
- SWR, use-debounce — довідники, пошук і перевірка оплати.
- Iron Session — зашифровані сесії та токени оформлення/повернення.
- sanitize-html — очищення HTML описів; текстові теги без атрибутів.
- nuqs — стан фільтрів каталогу в URL.
- Zustand — миттєвий стан кошика й улюблених у браузері.

`react-select` використовує Emotion навіть з `unstyled`. Кореневий
`EmotionRegistry` створює окремий cache на рендер, збирає правила через
підтримуваний `cache.insert` та передає їх у `useServerInsertedHTML` перед
відповідною порцією HTML. `cache.compat` запобігає inline-тегам `style`
всередині полів, які спричиняють розбіжність гідратації у streaming checkout.
Клієнт підхоплює серверні правила за `data-emotion`; CSS Modules залишаються
основою оформлення. Адаптер потрібен для зв'язку Emotion з App Router;
власного механізму CSS-in-JS або вимкнення SSR полів немає.

## Улюблені

`favorites-store.ts` створює окремий Zustand store для кожного `FavoritesProvider`;
серверні запити не ділять глобальний стан. Компоненти використовують селектори:
сердечко читає належність одного товару, шапка — кількість, сторінка — список ID.
У сховищі немає копій цін, залишків або об'єктів каталогу.

Zustand `persist` зберігає лише `ids` у `localStorage` під ключем
`curly-joy-favorites`. Завантаження починається після монтування, щоб серверний
HTML збігався з першим клієнтським рендером. До завантаження кнопки недоступні,
а сторінка показує стан завантаження замість помилкового порожнього списку.

`favorites-storage.ts` — адаптер стандартного `PersistStorage`: він потрібен
для читання старого формату `string[]` під тим самим ключем. Перший запис
переходить на `{state: {ids: string[]}, version: 1}`. ID очищуються від
дублікатів і некоректних елементів зі збереженням порядку. Читання не записує
дані назад; події `storage`, зокрема очищення сховища, перечитують актуальний
список без циклу записів. Паралельні зміни в різних вкладках мають семантику
останнього запису; це локальний список, без серверного вирішення конфліктів.

Якщо сховище недоступне або переповнене, зміни залишаються в пам'яті вкладки,
а спільне повідомлення пояснює, що вони не збережені. Наступний успішний запис
зберігає весь поточний список і прибирає помилку. Пошкоджені або невідомі версії
даних не перезаписуються під час завантаження. Статуси завантаження й помилок
не зберігаються; їх оновлення не викликає запису в браузер.

Синхронізації улюблених із CRM зараз немає. Коли CRM надасть контракт та
ідентифікацію покупця, до фічі потрібно додати Server Actions і правила
об'єднання гостьового списку, повторів, конфліктів та очищення при виході.
UI залежить від стану й операції `toggle`, а браузерний формат ізольований
в адаптері; контракт CRM не потрібно закладати в компоненти товарів.

## Дані й кеш

Загальні списки каталогу використовують `"use cache"`, `cacheLife("minutes")`
і теги `catalog`, `catalog:collection:<slug>`. Ціни й залишки на сторінці товару
читаються зі спільного для всіх відвідувачів `'use cache: remote'` на 30–60 с
з тегом `catalog`: CRM дає одну квоту запитів на токен для всього сайту, тож
перегляди товарів (будь-який трафік і вигадані slug) коштують їй не більше
двох читань каталогу на хвилину. Помилка CRM не кешується. Персональні дані,
додавання товару, відкриття кошика та checkout читають CRM наживо, поза кешем.
Зміна кількості й видалення у відкритому кошику перераховуються в Zustand
без звернення до CRM та без Server Action.
Обробника вебхука `catalog.changed` у проєкті поки немає; тег дає змогу
скидати кеш, коли він з’явиться.
CRM транспорт використовує `cache: "no-store"`.
Неповна або некоректна пагінація завершує читання помилкою.

Cookie `cjp_cart_v2` містить `{revision, lines: [{p: variantId, q: quantity}]}`:
позиції та UUID ревізії змінюються одним записом. Старий масив позицій також
читається й отримує ревізію при редагуванні або перед надсиланням checkout.
Браузер записує його після локальної зміни, щоб прямий перехід на checkout
бачив той самий кошик. Запис змінює лише відредаговану позицію: позиції,
змінені в іншій вкладці або не показані на сторінці, зберігаються без
попереджень. Якщо cookie не прийняв зміну, кошик повертає попередню кількість.
Покупця не просять перезавантажувати сторінку: склад, ціни й залишки
перевіряє checkout під час відкриття та підтвердження замовлення, а Server
Action сам оновлює форму через `refresh()`. Посилання на checkout виконує звичайну навігацію,
щоб не взяти старі дані з клієнтського кешу Next.js. Старий HttpOnly cookie `cjp_cart` читається лише до
першого запису нового формату. Порожній новий cookie містить `lines: []`, щоб старий
кошик не з’явився знову. Сервер перевіряє формат cookie й актуальні ціни та
залишки через CRM при відкритті кошика і перед замовленням.
Нульовий залишок не приховує товар,
але забороняє покупку. `stock: null` означає, що облік кількості не ведеться.
Сума обчислюється в цілих копійках із перевіркою безпечного діапазону.

## Checkout і оплата

Checkout перевіряє актуальний кошик, суму, доступні способи та refs адреси.
Якщо сума, кількість або показані умови безкоштовної доставки змінилися,
покупець підтверджує оновлену форму. Зміна доступних способів у CRM оновлює
вибір форми, очищає залежні поля адреси та застарілу знижку для іншої доставки.
Захищений токен форми забезпечує однаковий externalId для паралельних повторів
того самого запиту; завершена покупка не блокує нове замовлення з нової форми.
CRM присвоює номер замовлення й створює посилання Monobank.

Повернення використовує `/checkout/success?token=…`; токен дає доступ лише до
одного замовлення протягом 24 годин. Статус і сума читаються з CRM.
Посилання після відмови банку й COD також містять токен; стара сторінка без
токена перенаправляє на захищену адресу для замовлення з наявної сесії.
Токен зберігає також спосіб оплати та, для нового кошика, його ревізію.
Без cookie замовлення відновлюється через токен; сесія записується лише в Server Action.
Відсутній/нечинний токен і відсутня сесія показують відновлення, а не 404.
Затримка банку показує індикатор і перевірку кожні 5 секунд до хвилини.
Server Action повертає ревізію кошика лише після підтвердження оплати або COD.
Браузер очищає кошик синхронно, тільки якщо поточна ревізія збігається з
купленою. Серверна синхронізація платежу не записує cart cookie, тому її
затримана відповідь не перезаписує новий кошик. Старі квитанції без ревізії
не дозволяють автоматичного очищення. Незмінена квитанція не перезаписується.

Локального журналу замовлень, банківського callback і mock-провайдерів немає.
Webhook банку та створення ТТН належать CRM. Подробиці: [crm-checkout.md](./crm-checkout.md).

## Запит на оптовий доступ (B2B)

`/business` — форма запиту для зоомагазинів, грумерів, ветклінік. Заявка
стає лідом CRM із джерелом `partner` (`POST /leads`, `source: "partner"`),
окремо від роздрібних звернень. Ключ ідемпотентності `b2b-<uuid>` генерує
браузер один раз на форму, тож повторне натискання не створює дубль.
Менеджер узгоджує умови, оформлює контрагента й запрошує партнера до
кабінету партнера в CRM. Посилання «Увійти до кабінету партнера» й «Ввести
код» ведуть на `PARTNER_PORTAL_URL` (за замовчуванням
`https://obriym-crm.com/portal`).

Кабінет роздрібного покупця на сайті не будується: це функція Obriym CRM на
адресі магазину (`{shop}.obriym.app`). Варіант кабінету в дизайні сайту
лежить у гілці `feature/customer-cabinet` як платна кастомна доробка.

Адресу кабінету сайт не зберігає: її віддає CRM у `GET /capabilities` →
`customerAccount.url`, лише поки кабінет відкритий (`null`, якщо його вимкнено
чи не налаштовано). Іконка «Особистий кабінет» у шапці й пункт мобільного меню
з’являються тільки тоді. Відповідь кешується на 5 хвилин, тож вмикання й
вимикання в CRM доходить до сайту за 5 хвилин без релізу; коротший кеш змусив
би й статичні сторінки оновлюватися щохвилини, бо шапка є на кожній.
Якщо CRM недоступна, шапка рендериться без іконки
(`src/features/customer-account/queries.ts`).

Checkout починається з контактів і не вимагає входу або підтвердження
профілю. Окремий блок авторизації прибрано після уточнення маркетингового
сценарію. Кабінет лишається зовнішнім сервісом CRM. Попап із контактом,
персональний промокод, серверна перевірка першої покупки та облік
конверсій описані в [promotions-plan.md](./promotions-plan.md).
Реалізований контракт попапа, промокодів, підсумку checkout та налаштування
CRM описані в [promotion-integration.md](./promotion-integration.md).
Відгуки, рейтинг, лічильник клієнтів і скріни з Instagram на головній
описані в [social-proof.md](./social-proof.md).

## Пошукові системи

`src/app/sitemap.ts` збирає головну, каталог, категорії й товари з кешованого
каталогу CRM та інфосторінки; чернетки (`draft` у `src/content/info-pages.ts`)
отримують `noindex` і в sitemap не потрапляють. `src/app/robots.ts` закриває
кошик, checkout, обране й `/api/`. Індексовані сторінки мають canonical:
сортування, колекції й пошук у `/catalog?...` вказують на `/catalog`.

Open Graph будується через `openGraph()` з `src/lib/metadata.ts`: Next
зливає метадані поверхово, тож сторінка, що задає власний `openGraph`, інакше
втратила б назву сайту, локаль і картинку. Загальна картка —
`public/og-image.jpg` (1200×630, вирізана з hero), товар показує своє фото.
JSON-LD товару рендериться поруч із видимою ціною з того самого свіжого
читання; без фото блок `Product` не виводиться (Google вимагає зображення),
хлібні крихти лишаються. Логотип не передзавантажується й має `sizes`;
головне фото товару — `fetchPriority="high"`.

Колекції CRM мають власні сторінки `/collection/{slug}` (заголовок, опис,
canonical); плитки й полиця рекомендацій на головній ведуть туди, лише коли
колекція жива в CRM, інакше — у каталог. `?collection=` з невідомою назвою
не читає CRM: назва звіряється з кешованим списком колекцій. Товар,
категорія й колекція без тексту в CRM отримують запасний мета-опис. Головна
описує магазин (`OnlineStore`, `WebSite`) даними з `src/lib/site.ts`, товар
має `aggregateRating` з опублікованих відгуків CRM. Іконки — `apple-icon.png`
і `manifest.ts` (192/512 з логотипа). Emotion для react-select підключено
лише в `src/app/checkout/layout.tsx`.

Сторінки товару, категорії, колекції та інфосторінки читають `params` до
першого `<Suspense>` і мають `export const instant = false`. Перевірено на
`next build` + `next start`: з Partial Prefetching перший запит до адреси,
якої не було під час збірки, отримує App Shell зі статусом 200, а `notFound()`
чи `permanentRedirect()` спрацьовують уже в потоці (`noindex` або клієнтське
перенаправлення). Next тим часом рендерить адресу у фоні й кешує результат,
тож кожен наступний запит отримує справжній 404 або 308. Якби `params`
читалися всередині `<Suspense>`, і повторні запити лишалися б 200. Щоб 404
був і з першого запиту, довелося б відмовитися від App Shell для цих маршрутів.

## Семантика й перевірки

Нативні форми, кнопки, списки, таблиці й заголовки; контакти — `address`,
характеристики замовлення — `dl/dt/dd`. Поля підтримують клавіатуру,
прив’язані назви, повідомлення та фокус помилок.

Перевірки: `npm run typecheck`, `npm run lint -- --max-warnings 0`, `npm test`.
Browser QA, callback банку, production і база даних потребують окремих доказів.
Production build виконується лише за прямим запитом користувача.
