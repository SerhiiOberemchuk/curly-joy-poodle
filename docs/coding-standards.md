# Обов’язковий стандарт коду

Правила встановлено за вимогами власника проєкту. Короткий перелік у
[AGENTS.md](../AGENTS.md) є обов’язковим входом для кожної зміни.

## Проєктування та читабельність

Перед реалізацією визначити сценарій користувача, джерело даних, контракт
функції, її інваріанти та поведінку при помилках і повторному запиті.
Одна функція повинна мати одну чітку відповідальність. Стан зберігати в одному
місці, похідні значення обчислювати. Межі сервера і клієнта робити явними.
Не додавати абстракції для уявних майбутніх вимог, невикористаний код,
дублікати перевірок або коментарі, що лише переказують реалізацію.

## Бібліотеки та версії

Спочатку використовувати можливості платформи й підтримуваних бібліотек.
Не писати власні аналоги форм, валідації, combobox, кешу запитів або криптографії.
Для винятку описати, чому стандартний механізм не відповідає вимозі, і залишити
найменший можливий адаптер із перевіркою його контракту.

Оновлювати залежності до актуальних сумісних версій за офіційною документацією.
Перевіряти весь граф залежностей, peer dependencies і lockfile; не ремонтувати
лише перший пакет, який повідомив про помилку. Заборонено примусове встановлення
несумісних пакетів. Зміна major-версії потребує перевірки міграції.

Компілятор проєкту — TypeScript 7 (`npm run typecheck`). Compiler API для ESLint
забезпечується офіційним пакетом сумісності TypeScript 6, оскільки нативний
компілятор не надає старий JS Compiler API. Це не дозвіл використовувати TS6
замість компілятора проєкту. `npm run lint -- --max-warnings 0` має проходити.

## Next.js і серверна логіка

Використовувати актуальні можливості встановленого Next.js після читання
відповідного розділу `node_modules/next/dist/docs/`. Дотримуватись застережень
про зміни API та deprecated-механізми.

Компоненти серверні за замовчуванням. Client Component потрібен лише для
інтерактивності. Маршрути компонують сторінку; бізнес-логіка живе у фічах.
Браузер викликає Server Functions / Server Actions. Не створювати додаткові
локальні HTTP API для бізнес-дій. Зовнішні API викликати на сервері; секрети
захищати `server-only`. Route Handler залишати лише там, де зовнішній протокол
вимагає HTTP endpoint, із поясненням цього контракту.

Вхідні дані перевіряти на сервері незалежно від клієнтської валідації.
Зовнішні відповіді перевіряти на межі інтеграції. Приведення типу не є валідацією.
Для фінансових операцій обов’язкові захист повторного запиту та достовірний стан.

## CRM та оплата

CRM — джерело даних каталогу, цін, залишків, замовлень, платежів і доставки.
Не вигадувати fallback-значення й не показувати draft-товари. Нульовий залишок
не приховує товар, але забороняє покупку. Невідстежуваний залишок не означає нуль.
Перед створенням замовлення повторно перевіряти актуальні ціни та кількість.

Monobank і Нова пошта керуються через CRM. Повернення покупця з банку не означає
успішну оплату: показувати очікування й перевіряти CRM. Не створювати повторний
платіж лише через затримку підтвердження. Не очищати новий кошик через оплату
попереднього замовлення. Дані сесії не розкривати через публічний номер замовлення.

## HTML-семантика та доступність

Використовувати нативні `button`, посилання, форми, списки, таблиці та заголовки
відповідно до їхнього призначення. Сторінка має один головний `h1` і послідовну
ієрархію заголовків. `section` позначає тематичний розділ із доступною назвою,
а `div` — лише контейнер верстки. Не вкладати інтерактивні елементи один в одного.

Кожне поле має доступну назву; помилка пов’язана з полем. Перевіряти клавіатурний
вибір, фокус, Escape і оголошення змін статусу. Не застосовувати ARIA замість
наявної нативної семантики. Для анімації враховувати `prefers-reduced-motion`.
Контактні дані позначати `address`, пари назва/значення — `dl`, `dt`, `dd`.

## Перевірки та документація

Для змін логіки перевіряти поведінку та відмови, а не копіювати реалізацію тестом.
Для невеликих оборотних правок достатня відповідна перевірка; не додавати
непотрібні тести чи окремий framework без причини. Перевірки:

- `npm run lint -- --max-warnings 0`;
- `npm run typecheck`;
- `npm test` для змін логіки;
- перевірка зміненого інтерфейсу в браузері, коли інструмент доступний.

Production build не запускати без прямого запиту користувача. Тести, browser QA,
перевірка банку, база даних і deployment — окремі види доказів. Обмеження перевірки
вказувати явно. Документацію оновлювати разом із контрактом і поведінкою.
Не делегувати написання коду іншим агентам без прямого доручення користувача.
