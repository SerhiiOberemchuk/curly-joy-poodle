# Аудит checkout — 2026-10-28

Перевірено зв’язок кнопок і вибраних значень із Server Actions, створенням
замовлення, повторною оплатою, довідниками Нової пошти, промокодами та
поверненням із банку. Первинний аудит був без змін бізнес-логіки;
наступним етапом власник доручив виправити підтверджені проблеми.
Попереднє виправлення неактивної кнопки після підтвердження оплати збережено.

## Поточний стан

Усі чотири наведені нижче проблеми виправлено:

- Сторінки після відмови банку та COD містять захищений токен свого замовлення.
  Стара адреса без токена перенаправляє на токенізовану. Оплата та перевірка
  статусу без токена не використовують поточну cookie іншого замовлення.
- Форма узгоджує вибір із новими можливостями CRM, зберігає контакти,
  очищає адресу при зміні доставки та відкидає застарілий результат промокоду.
- Сервер звіряє показані умови безкоштовної доставки до створення замовлення;
  зміна потребує повторного підтвердження оновленого підсумку.
- Кошик містить ревізію разом із позиціями. Оплата не очищає його на сервері:
  браузер звіряє поточну ревізію після відповіді. Новий кошик, включно з
  ідентичним складом, зберігається. Старий формат мігрує без втрати позицій;
  старі квитанції без ревізії не дозволяють автоматичного очищення.

Регресійні сценарії включені в `inventory.test.cjs`, `checkout-form.test.cjs`
та `cart-controls.test.cjs`. Додатково перевіряються COD без cookie,
повтор прийнятої форми без присвоєння нового кошика старому замовленню,
застарілий quote після зміни умов доставки та затримана відповідь оплати.

## Початкові відтворення (до виправлень)

### 1. P1 — кнопка оплати зі старої вкладки може відкрити оплату іншого замовлення

Місця: `src/features/checkout/checkout.server.ts:391`,
`src/app/checkout/success/page.tsx:57`,
`src/features/checkout/checkout.server.ts:404`.

Після прийняття замовлення та невдалого відкриття банку сервер повертає
`/checkout/success?payment=unavailable` без токена конкретного замовлення.
Кнопка «Перейти до оплати» та перевірка статусу на цій сторінці прив’язані
до `token === undefined`, тому дія повторно читає поточну квитанцію з cookie.

Відтворення:

1. Створити карткове замовлення A; банк недоступний, сторінка показує A
   і кнопку переходу до оплати.
2. У другій вкладці створити замовлення B з іншим складом/кількістю товарів.
   Спільна cookie тепер містить квитанцію B.
3. Натиснути кнопку оплати на залишеній сторінці A.
4. Запит платіжного посилання адресовано externalId замовлення B.

Підтверджено локальним сценарієм зі справжніми `placeOrderAction`,
`retryPaymentAction`, квитанціями й побудовою платіжного запиту; транспорт CRM
замінено тестовим. Реальних замовлень і платежів не створено.

Виправлення: всі сторінки підтвердження, включно з відмовою банку та COD,
мають передавати підписане підтвердження саме показаного замовлення;
перевірка статусу та повторна оплата повинні використовувати його.

### 2. P2 — після оновлення можливостей CRM кнопка надсилає прихований старий вибір

Місце: `src/features/checkout/components/checkout-form.tsx:94`.

Доступні радіокнопки будуються з поточних `capabilities`, але `useForm`
отримує способи оплати та доставки лише через початкові `defaultValues`.
При оновленні props значення форми не узгоджуються з новими варіантами.

Відтворення в React Testing Library зі справжнім `CheckoutForm`:

1. Заповнити форму: картка + відділення.
2. Оновити props: у CRM залишилися тільки COD + кур’єр.
3. Старі радіокнопки зникають, нові залишаються невибраними; поле відділення
   та напис «Перейти до оплати» залишаються.
4. Кнопка активна та надсилає `payment=card`, `delivery=np-branch`.

Сервер повторно перевіряє доступність способів і відхиляє цей вибір;
це не обхід серверної валідації. Проблема — невідповідність видимого стану
дії кнопки та повторення відмови до ручної зміни вибору покупцем.

Виправлення: при зміні доступних варіантів узгоджувати вибір форми,
очищати залежні поля адреси та результат промокоду, якщо змінилася доставка.

### 3. P2 — безкоштовна доставка може стати платною без повторного підтвердження

Місця: `src/features/checkout/checkout.server.ts:208`,
`src/features/checkout/checkout.server.ts:276`.

Сервер звіряє показану суму товарів, але не звіряє показані покупцеві умови
доставки. `freeShipping` береться зі свіжого кошика без окремого повідомлення
про зміну цих умов.

Відтворення: форма показує товари на 420 грн і безкоштовну доставку
при порозі 400 грн. До надсилання CRM змінює поріг на 500 грн. Сума товарів
залишається 420 грн, тому оформлення проходить одразу; в запиті замовлення
вже зазначено «Доставка за тарифами перевізника».

Виправлення: включити показані умови доставки в перевірку очікувань покупця;
при зміні оновити підсумок і запросити повторне підтвердження.

### 4. P2 — оплата попереднього замовлення очищає заново зібраний ідентичний кошик

Місця: `src/features/checkout/payment/settlement.ts:38`,
`src/features/checkout/checkout-attempt.ts:28`.

Захист очищення порівнює тільки variantId та кількість. Він зберігає кошик
з іншим складом, але не розрізняє попередній кошик і новий з тим самим складом.

Відтворення: розпочати оплату A з одним товаром; очистити кошик і знову
додати цей товар у тій самій кількості; підтвердити оплату A. Наступна
синхронізація очищає заново зібраний кошик.

Виправлення: додати ідентичність/ревізію кошика та звіряти її при очищенні;
самого відбитка складу недостатньо. Врахувати також зміну браузерного кошика
під час уже запущеної серверної синхронізації.

## Перевірені захисти та відповідність кнопок

| Сценарій | Результат перевірки коду та наявних тестів |
| --- | --- |
| Порожній кошик / сума нижче мінімальної | Оформлення недоступне; сервер також перевіряє |
| Зміна ціни або залишку | Свіжа перевірка CRM, зупинка до підтвердження оновленого кошика |
| Повторне надсилання того самого payload і токена | Той самий externalId; повтор використовує прийняте замовлення |
| Очікування відповіді оформлення | Кнопка й поля блокуються, показується «Оформлюємо…» |
| Вибір іншого міста / способу доставки | Залежні поля очищаються для звичайної зміни покупцем |
| Помилка довідника Нової пошти | Є дія повторного завантаження; адреса перевіряється на сервері |
| Введений, але не перевірений промокод | Оформлення блокується до застосування або видалення коду |
| Зміна email / доставки / товарів після quote | Попередній результат знижки не використовується |
| Затримана відповідь quote для старого email | Не відновлює стару знижку |
| Успішна оплата | Визначається за CRM; кнопка «Оплату підтверджено» неактивна |
| Очікування банку | Періодичні перевірки до хвилини, потім ручна перевірка |
| Відмова банку після створення замовлення | Повторна оплата того самого замовлення, з обмеженням із пункту 1 |
| Скасування / повне чи часткове повернення | Немає кнопки повторної оплати для цих станів |
| Недоступність CRM | Немає вигаданого успіху, зберігається можливість перевірити пізніше |
| Повернення з підписаним токеном без cookie | Відновлення з CRM; підроблений токен не відкриває дані |

## Межі доказів

Чотири проблемні сценарії відтворено окремими локальними перевірками на
наявних тестових harness. Проходження цих перевірок підтверджує наявність
описаної проблемної поведінки, а не її виправлення. Тимчасові файли сценаріїв
видалено після перевірки; кроки відтворення залишено вище.

Початковий аудит: 171 тест, TypeScript і ESLint пройшли. Після виправлень:
`npm test` — 183 тести пройшли; `npm run typecheck` — пройшов;
`npm run lint -- --max-warnings 0` — пройшов без помилок і попереджень.
У Chrome перевірено серверний HTML справжньої сторінки для paid, COD і unpaid
із локальними тестовими даними: неактивне підтвердження оплати, відсутність
онлайн-оплати для COD, доступна оплата для unpaid. Це перевірка станів
інтерфейсу, без гідрації та без живого CRM/банківського сценарію.
Наскрізний сценарій із реальним Monobank callback, production,
деплой і production build не виконувалися. Живих записів у CRM,
замовлень, платежів або ТТН не створено.
