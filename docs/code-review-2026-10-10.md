# Рев’ю коду й семантики — 10 жовтня 2026

Рев’ю охоплює storefront, каталог, кошик, checkout, повернення з оплати,
межі CRM, залежності та HTML-семантику. Частина виправлень уже збережена
в коміті `0c89613`; решта належить поточним змінам. Це не аудит production CRM.
Стандарт закріплено в [AGENTS.md](../AGENTS.md) і [coding-standards.md](./coding-standards.md).

## Залишкові питання

1. **P1, контракт CRM:** отримання/створення платіжного посилання має послідовність
   GET → за відсутності POST. Без атомарної гарантії CRM два одночасні запити
   можуть обидва перейти до створення інвойсу. Один externalId захищає замовлення,
   але сам собою не доводить ідемпотентність банківського інвойсу. Це ризик за
   кодом контракту; живу гонку банку не запускали. Гарантія має належати CRM,
   локальна Map/блокування одного процесу її не забезпечить.
2. **P2, кошик:** fingerprint захищає змінений кошик після оплати, але не розрізняє
   видалений і заново створений кошик із точно тими самими позиціями/кількостями.
   Для цього потрібен окремий ідентифікатор покоління кошика; поточні тести
   підтверджують збереження кошика з іншими позиціями/кількостями.
3. **P2, API Нової пошти:** CRM повертає до 500 пунктів на місто. Пошук працює
   за отриманим довідником; збільшення повноти потребує зміни CRM API.
4. **P2, dev-залежності:** повний npm audit показує 5 high через
   braces → micromatch → fast-glob → ESLint Next. Для
   [braces advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
   виправленої версії немає. Запропонований npm force-відкат eslint-config-next
   до 14 не застосовано: він руйнує сумісність із Next 16. Production dependencies
   (`npm audit --omit=dev`) — 0 відомих вразливостей на момент перевірки.
5. **Посилання, видані раніше:** повернення без токена потребує старої cookie.
   Оновлення сайту не переписує URL вже відкритого банківського інвойсу.
   Без cookie або чинного токена дані замовлення не розкриваються за номером.

## Докази й межі перевірки

- TypeScript 7 та ESLint перевіряються стандартними скриптами проєкту.
- 56 автоматизованих сценаріїв: залишки, ціни, помилки CRM, refs доставки,
  повтори/паралельність замовлення, криптографічні токени, повернення без cookie,
  pending → paid, недоступна CRM, пошук відділення, клавіатура, меню, посилання добірки.
- Axe-core перевіряє DOM/ARIA форми для відділення й кур’єра в JSDOM.
  Color contrast вимкнений через відсутність layout; це не доказ повної WCAG-відповідності.
- Живе читання CRM перевірило контракт 30 товарів, 4 категорій, 0 колекцій.
  Жодних живих замовлень, платежів або ТТН ці перевірки не створювали.
- Локальний Next dev на порту 3001: `/checkout/success` без cookie відповідає
  HTTP 200, містить допомогу з відновлення й не містить маркера Next error page.
- Browser connector повертає `missing field sandboxPolicy`; візуальні розміри,
  перекриття блоків і реальний браузер цим прогоном не підтверджені.
- Production build, деплой, реальний Monobank callback та база CRM не перевірені.

## Обґрунтовані адаптери

Власний slugify відображає канонічну транслітерацію URL CRM. Його заміна
загальним пакетом без міграції URL може зламати чинні посилання; він лишається
вузьким адаптером контракту. Криптографію надає Iron Session, HTML-парсер —
sanitize-html, поля вибору — react-select; власних аналогів цих бібліотек немає.
